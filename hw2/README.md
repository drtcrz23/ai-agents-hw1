# ДЗ-2

## Выбор конфигурации из ДЗ-1

Для ДЗ-2 и итогового проекта берем **Qwen3.5-9B Q4_K_M через LM Studio**:

- против Q8_0: **+45-50% к скорости генерации**
- кривая TTFT из ДЗ-1: при входе 8к токенов TTFT - 20 с, при 16к - 42 с, при 32к - 93 с.

Отсюда **токен-бюджет ДЗ-2 - 6-8к токенов на вход одного вызова модели**
(системный промпт + история + чанки поиска + вопрос): это зона TTFT - 15-20 с, сумма по всем вызовам агента на вопрос может превышать бюджет и не должна приближаться к проверенному в ДЗ-1 пределу 32к

## Архитектура

```
data/docs (20 PDF) ingest.py ─> чанки -> nomic-embed -> index/ (vectors.npy + chunks.json + meta.json)

question baseline.py ─> 1-search
question agentic.py ─> LLM <-> search(query) tool-calling (>=2 поиска) ─> ответ + sources
question memory_session.py ─> история + summarization + checkpoint (sessions/*.json)

run_eval.py: recall@k индекса; baseline vs agentic (качество, поиски, токены) -> results/eval.json
```

- **Embedding**: `text-embedding-nomic-embed-text-v1.5` (LM Studio, локально, 768-dim).
  bge-m3 через Ollama не понадобился, для корпуса из ~2000 чанков
  качества достаточно (recall - ниже)
- **Индекс на диске**: `index/vectors.npy` (L2-нормированные векторы, косинусная
  близость через матричное умножение) + `index/chunks.json` + `index/meta.json`
- **Поиск**: `search(query, k)` возвращает текст чанка, файл-источник, индекс чанка,
  позицию и score

## Чанкинг и его обоснование

Стратегия: **разбиение по абзацам с накоплением до ~300 токенов (1050 символов),
overlap 50 токенов (175 символов)**; приближение 1 токен это 3.5 символа для
английского научного текста. Абзац длиннее лимита режется по границам
предложений (`split_long_para`), поэтому лимит соблюдается и на PDF-страницах,
где вся страница извлекается одним абзацем.

Обоснование:
- **300 токенов** это размер абзаца научного текста: чанк semantic-цельный
  (не рвет посреди предложения/таблицы), при этом в top-5 помещается 5 разных
  фрагментов
- **overlap 50 токенов** (~1/6 чанка) страхует от разрыва факта на границе чанков;
- разбиение **по абзацам**

Фактический индекс: 20 документов -> **2047 чанков**, медиана 1143 символа
(~330 токенов с учетом overlap-хвостов), максимум 2689 символов (редкие длинные предложения не режутся посреди фразы).

## Корпус

## Золотой набор и recall@k

`data/golden/golden_set.json`: 20 вопросов, из них 5 мульти-хоп (требуют сведений
из 2-3 документов: Dapper vs Canopy, Spanner vs CockroachDB, Spanner vs FoundationDB,
TAO vs memcache, Seer vs Sage vs Sinan).

recall@k (k = 1, 3, 5) считается по доле expected_docs, попавших в top-k поиска;
отдельно - по мульти-хоп подмножеству. Результаты: `results/eval.json`, таблица - ниже.

## Agentic vs Baseline

- **Baseline** (`baseline.py`): вопрос -> один search -> 5 чанков -> ответ
- **Agentic** (`agentic.py`): модель получает tool `search(query)`, сама формулирует
  запросы (в т.ч. параллельно несколько в одном ходе), минимум 2 поиска за ответ, если модель
  пытается финализировать после < 2 поисков, цикл делает один nudge-ход с просьбой
  добрать вторым запросом; цикл до 6 ходов. каждый query модели, результаты поисков целиком, финальный ответ пишутся в `logs/*agentic*.log`

Метрики сравнения (по каждому вопросу):
- **покрытие источников** - доля expected_docs, названных в строке `Sources:`
  ответа. Это метрика coverage, **а не фактической правильности ответа**: она
  показывает, что модель опиралась на нужные документы, но не проверяет сами
  факты (expected_facts в golden set - для ручной проверки, см. Ограничения);
- **стоимость** - число поисков, prompt/completion токены на вопрос.

## Контекст и память

`memory_session.py` - мультитерн-диалог:
- **История**: последние ходы дословно; при превышении `HISTORY_CHAR_LIMIT`
  (10к символов == 3к токенов) старая история сжимается в summary промптом
  «сохрани все факты, имена, числа, источники», summary подмешивается в system-сообщение.
- **Бюджет** обоснован кривой ДЗ-1: summary ~1К + свежие ходы ~2К + вопрос
- **Checkpoint/resume**: состояние диалога (summary + history) сериализуется в
  `sessions/*.json` после каждого хода; новый запуск `python3 memory_session.py
  demo.json ask "..."` подхватывает диалог с места остановки

## Запуск

Все команды выполняются из `hw2/scripts/` (скрипты импортируют `common.py`
из своего каталога - Python добавляет каталог запускаемого скрипта в `sys.path`).
Пути ниже - из корня репозитория `hw1`

```bash
pip3 install requests numpy pypdf
# LM Studio: загружен qwen/qwen3.5-9b (Q4_K_M, reasoning off) и
# text-embedding-nomic-embed-text-v1.5, сервер на http://127.0.0.1:1234
cd hw2/scripts
python3 ingest.py
python3 search.py "query" # smoke-тест поиска
python3 run_eval.py # recall@k + baseline vs agentic (~40 мин)
python3 memory_session.py demo.json ask "..." # мультитерн с checkpoint
python3 agentic.py "question" # одиночный мульти-хоп ответ с трассой в лог
```

итоговые метрики в `results/eval.json`.

## Результаты

Полный прогон: `logs/2026-10-29T22-58-27-eval.log`, метрики: `results/eval.json`.
Reasoning-режим модели выключен, temperature 0.
Индекс - 2047 чанков

### recall@k индекса (20 вопросов, 5 мульти-хоп)

| Метрика | все | мульти-хоп |
|---|---|---|
| recall@1 | 0.87 | 0.47 |
| recall@3 | 0.91 | 0.63 |
| recall@5 | **0.95** | 0.80 |

Все 15 single-hop вопросов найдены с первого раза (recall@1 = 1.0 у всех).
На мульти-хопе один запрос редко покрывает обе стороны сравнения
(Dapper vs Canopy), поэтому агенту нужно >= 2 целенаправленных поиска -
что он и делает.

### Agentic vs Baseline

| Метрика | Baseline | Agentic |
|---|---|---|
| Покрытие источников (средняя) | 0.933 | **0.942** |
| - сингл-хоп | 1.00 | 1.00 |
| - мульти-хоп | 0.733 | **0.767** |
| Поисков на вопрос | 1.0 | 2.0 |
| Prompt-токенов на вопрос | 1 444 | 6 202 |
| Completion-токенов на вопрос | 256 | 456 |
| Всего токенов на вопрос | 1 700 | 6 659 |

Выводы:
- **Agentic выигрывает у baseline там, где это ожидаемо - на мульти-хопе**
  (0.767 против 0.733; сингл-хоп - паритет 1.00/1.00): при мелких чанках
  топ-5 первого поиска реже накрывает обе стороны сравнения, и второй
  целенаправленный поиск агента добирает недостающее. На крупном чанкинге
  (первый прогон) этого отрыва не было видно
- **Цена agentic**: *2 поисков, *4.3 prompt-токенов на вопрос (6 202 против
  1 443; по total - *3.9, 6 659 против 1 700), каждый ход цикла несет
  накопленный контекст + результаты поисков. При этом **вход каждого вызова**
  остается в бюджетной зоне, а completion растет умеренно.
- **Оговорка про метрику качества**: «покрытие источников» проверяет,
  названы ли ожидаемые документы в `Sources:`, но не проверяет сами
  факты ответа

## Известные ограничения

- **Summarization теряет факты** - сохраненный summary в
  `sessions/demo_multiturn.json` содержит две фактические ошибки, которых не
  было в исходных ходах: CockroachDB названа «Paxos-based» (на деле Raft) и
  приписаны «vector clocks» (на деле гибридные логические часы HLC). сжатие безвозвратно переписывает историю, и неверный
  summary продолжает порождать неверные ответы во всех последующих ходах.
  Это осознанное ограничение выбранного варианта памяти
- Recall и «покрытие источников» считаются по doc_id: чанк-уровень оценивает
  индекс, и `Sources:`-строка - что модель опиралась на нужные документы,
  но «факт найден/правилен» автоматически не проверяется (expected_facts
  в golden set - для ручной проверки ответов).
- При извлечении PDF теряется часть таблиц/формул (pypdf), чанки местами
  содержат мусор переносов - на recall не повлияло, но заметно в выдаче.
